What to look for

  • Written by on each claim records the host that inserted it. After a DR failover to NC2 the portal keeps its name; the address in the footer shows where it now runs.
  • DB served by is inet_server_addr(): the PostgreSQL node that answered. Behind HAProxy (stage 2) it changes when Patroni promotes a new primary.
  • The web tier never opens a database connection. Only the middleware does, so moving the middleware into pods later is a configuration change.
  • From stage 3 the document VM writes the photo to Files when the claim is submitted, and the accepted packet to Objects when the claim is moved to APPROVED. The portal does not mount the share and does not hold the Objects keys.
  • From stage 4 the API pods on NKP take both roles: the middleware container is the only database client, and the docs container in the same pod writes Files and Objects. The middleware on the portal VM is stopped. New claims show a pod name in Written by.
  • From stage 5 the chat pods answer questions on the main page. They call the NAI endpoint, and read claims, photos and packets only through the API pods: they hold no database or Objects credentials, and every tool is read-only. Fraud scores come from fixed rules in the middleware; the model explains them.
